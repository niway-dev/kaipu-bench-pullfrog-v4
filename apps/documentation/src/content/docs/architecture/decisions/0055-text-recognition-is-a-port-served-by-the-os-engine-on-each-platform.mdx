## Context

The owner wants the text inside a screenshot to be selectable, and recognized blocks offered
as targets to hide and, later, to zoom on, on every platform the app captures on (macOS and
Windows). The desktop app has no OCR today. The repository forbids install scripts and keeps
native code to one patched npm module and in-house Swift helpers built with `swiftc`
(`native/encoded-capture`, `native/cursor-capture`).

## Decision

1. **A port in main**, `TextRecognizer.recognize(png)`, returning words with a box in source
   pixels (top-left origin), a line index and a confidence, or `"unavailable"`.
2. **macOS backend:** Apple Vision in a Swift helper built and shipped like the existing
   helpers. It prints versioned JSON and runs under a timeout.
3. **Windows backend:** `Windows.Media.Ocr`, driven without a compiled npm module.
4. **Failure is "off".** A missing helper, a non-zero exit, a timeout or output that fails
   its schema all return `"unavailable"`; the editor works without the text tools.
5. **Cache.** Results are stored in `.kaipu/<id>.text.json`, keyed by asset. Saving a
   redaction removes the words it intersects.
6. **Only text.** The port does not return UI boxes; nothing produces them.

## M0 results (macOS, 2026-11-11)

Measured by the spike in `apps/kaipu-record/scripts/spikes/image-editor-m0/vision/`
([NIW2-697](https://linear.app/niway/issue/NIW2-697/image-editor-m0-spikes-for-color-memory-and-text-recognition-on-macos)):
a Swift helper built with `swiftc -O` (target `arm64-apple-macos13.0`) that takes a PNG path,
runs `VNRecognizeTextRequest`, and prints versioned JSON with word boxes in top-left source
pixels. A runner spawns it as a new process per run, the way main will, and measures wall
clock from spawn to exit. Fixtures are synthetic UI screenshots drawn with CoreText (window
chrome, sidebar, 11–13 pt labels, a table, a code line) with 119 ground-truth words.

- **Commands:** `apps/kaipu-record/scripts/spikes/image-editor-m0/vision/run.sh` on the M5,
  and `run-on-macmini.sh` (same folder) from the M5 for the mini.
- **Machines:** MacBook Pro M5 (Mac17,2, 24 GB), macOS 26.6.2; Mac mini M4 (Mac16,10, 16 GB),
  macOS 27.0.1. Swift 6.4.2 on both.

Wall clock in ms, `accurate` level, first run of that image in the bench, then the median and
maximum of five more processes; recall is ground-truth words recognized exactly:

| Machine  | Image              | First run (this bench) | Median | Max | Recall |
| -------- | ------------------ | ---------------------- | ------ | --- | ------ |
| M5       | 1920×1080, scale 1 | 1413                   | 561    | 577 | 86.6%  |
| M5       | 3024×1964, scale 2 | 539                    | 515    | 535 | 95.0%  |
| Mac mini | 1920×1080, scale 1 | 388                    | 212    | 236 | 99.2%  |
| Mac mini | 3024×1964, scale 2 | 214                    | 246    | 266 | 99.2%  |

- **Only the first row per machine can be cold, and the mini's table row is not.** The bench runs
  the 1920×1080 image first and the Retina one after it, so the Retina row follows a loaded
  model. On the mini the first run ever was killed at 10 s while the model compiled, and the one
  after it, by hand, took 13.5 s (below); both happened before the bench, so its 388 ms is a
  warm run. The table therefore shows warm numbers; the cold case missed the 1.5 s target on
  the mini.
- **The first recognition on a machine is much slower.** On the mini the first `accurate`
  run hit the 10 s timeout of the runner's first version (the committed runner allows 60 s); a stack sample showed the process waiting in
  `_ANEClient compileModel` (the Neural Engine compiling the model). Run again by hand, it
  took **13.5 s**; every run after that was warm (the rows above). The M5's 1413 ms was the
  first launch after the build, but the model may already have been compiled there, so it
  is not proven to be the coldest case. When the OS drops that compiled model (after an OS
  update, most likely) is not measured.
- The `fast` level is 2–3 times quicker (about 170–215 ms) but recognized only 44.5% of the
  words at scale 1, where interface text is 11–13 px high.
- The two machines recognize differently on the same image (86.6% and 99.2% at scale 1);
  which words the M5 missed, and whether macOS 27 is the reason, is not checked.

**What this decides for M8:**

- The macOS backend is viable: warm, a 1920×1080 image or a Retina screenshot is recognized
  in about 0.2–0.6 s, under the 1.5 s target.
- The helper uses the `accurate` level.
- The timeout must allow the one-time model compilation: at least 30 s for a call, and the
  editor shows the text tools as pending until the answer arrives, never blocking the canvas.
  A 10 s timeout would turn the first use on a machine into "unavailable".
- Recognition runs off the editing path, so the 13.5 s first run does not trigger "What would
  reopen this": that condition is about the per-image latency, which passed on both machines.
  The oldest supported Mac is not measured.

**Not measured:** the Windows backend (measured later in M10, below), recognition spawned from Electron's main
process, real screenshots instead of drawn fixtures, an Intel Mac, a recognition after reboot
or OS update.

## Alternatives rejected

- **One WASM engine everywhere (tesseract.js, PaddleOCR on ONNX).** A language-data download
  or tens of megabytes in the bundle, and weaker results on small interface text than the
  system engines. Kept as the fallback if the Windows spike fails.
- **An npm package that wraps Vision.** The ones found either compile at install, which the
  repository forbids, or ship a binary we did not build.
- **macOS only.** The owner asked for both platforms.
- **Recognition in memory only.** Slower reopen and no path to searching screenshots by their
  text; the owner accepts a local cache.

## Consequences

- A third Swift helper to build, sign and ship, with its own deployment target to state.
- Two engines give different words and boxes for the same image; tests assert on fixtures
  per platform, not on equal output.
- The text cache is one more file that must follow the item when it is moved or deleted.

## Implementation status

M8 ([NIW2-705](https://linear.app/niway/issue/NIW2-705)) builds points 1, 2, 4 and 5 for macOS,
behind the `image-text` flag, in the canvas editor and in the classic one. M10
([NIW2-707](https://linear.app/niway/issue/NIW2-707)) builds point 3. Usage and file layout:
[image editor text recognition](/backlog/image-editor-text-recognition/).

- **Port.** `TextRecognizer` and the `RecognizedWord` schema live in `@kaipu/domain/schemas`,
  not in main as point 1 says, so the renderer and main validate the same shape.
- **Helper.** `native/text-recognition/main.swift`, `accurate` level with language correction,
  macOS 13 or later, universal. The PNG arrives on stdin, so no copy of the screenshot is
  written to a temporary file. Main allows 45 s per call, for the first-run model compilation.
- **Cache key.** Each asset's entry carries the sha256 of the PNG bytes it was recognized from;
  a different image is recognized again instead of trusting a stale entry.
- **Redactions.** The renderer sends the words outside every baked redaction with each save, and
  main rewrites the file from them; a save without them deletes it. A recognition that finishes
  after a save, rename or delete of its item is discarded.
- **Windows backend.** `windows-ocr.ts` runs a PowerShell 5.1 script (absolute path under
  `%SystemRoot%`, never `pwsh`, which cannot load WinRT types) passed with `-EncodedCommand`. The
  PNG arrives base64 on stdin. The script uses the user profile's OCR languages, scales images
  above `OcrEngine.MaxImageDimension`, rotates boxes back by `TextAngle`, and prints the same
  versioned JSON as the Swift helper. Windows OCR has no per-word confidence, so every word
  reports 1. Main allows 30 s per call. Only a missing PowerShell is remembered for the session;
  any other failure, such as no OCR language pack, is retried on the next request. No compiled
  module, no npm dependency, nothing to sign: the same pattern as the Windows window lister.
- **Windows measurement.** Workflow `Text recognition (Windows)`, job `Recognize and measure
(Windows)`, running `bun apps/kaipu-record/scripts/measure-windows-ocr.ts` on a GitHub
  `windows-latest` VM (Windows Server 2025, 10.0.26100, AMD EPYC 9V74, 4 cores, 16 GiB,
  PowerShell 5.1.26100, OCR language en-US), 2026-11-11, run 43122488358. End to end per call,
  each a new PowerShell process:

  | Fixture (1920×1080)     | First call of the fixture                      | Next 4 calls |
  | ----------------------- | ---------------------------------------------- | ------------ |
  | sparse settings card    | 3353 ms (cold: first OCR call on the VM)       | 506–516 ms   |
  | dense, 3×3 copies of it | 753 ms (not cold: runs after the sparse calls) | 754–764 ms   |

  PowerShell start alone takes about 200 ms. All six lines were recognized exactly, boxes landed
  within a few pixels of the drawn text, and a 10° tilted copy put its boxes back on the text.
  This is a VM, not a consumer machine; nothing was measured on a real Windows 10 or 11 install.

The cold call is over the 1.5 s reopen condition below. For comparison, Vision's first run
on the mini took 13.5 s, and M0 decided that did not reopen the macOS backend because
recognition runs off the editing path; the Windows condition, unlike the macOS one, names the
cold case explicitly. Whether the Windows first-call cost recurs after every boot or only once
per machine, like Vision's model compilation, is not measured: the VM was new. What costs the extra 2.8 s is not
measured. The likely cause is the first load of the OCR engine and its language data on a fresh
machine, which a compiled helper would also pay; that is a hypothesis, not a result. The
backend ships as is, behind the flag, until the owner decides between keeping it, a compiled
helper and the WASM fallback. A cold call still fits the 30 s timeout, so the first recognition
is slow, not lost.

## Non-goals

Translation, handwriting, searching the Library by recognized text, recognizing text in video
frames, zoom targets in the video editor.

## What would reopen this

- M0 shows `Windows.Media.Ocr` cannot be driven without a compiled module, or takes more than
  1.5 s cold on a 1920×1080 image: decide between a small compiled helper and the WASM fallback.
- Vision takes more than 1.5 s on a Retina screenshot on the oldest supported Mac.
- Linux capture is added: it needs a backend, most likely the WASM fallback.
