## Context

The image editor edits one screenshot. Annotation coordinates are normalized to that shot
(`annotations/scene.ts`), the beautify frame wraps it, and crop is relative to the frame.
Saving flattens everything into `<id>.png`; reopening starts an empty scene over the flattened
pixels, as the [re-editable screenshots analysis](/backlog/screenshot-scene-doc/) describes.

The owner asked on 2026-11-11 for a canvas: the capture in the middle of an infinite surface,
objects allowed outside the image, more than one image, and an export that is "only the space
of the content". They also expect edits to remain editable after saving. Neither fits a model
whose coordinates belong to one image and whose only saved artifact is a flattened PNG.

## Decision

1. **One world space.** The editor's document is a list of items, images and annotations
   alike, positioned in world units. One world unit is one source pixel of an image at scale 1.
2. **The export is the content box.** Copy and Save render the union of all item bounds plus
   the beautify padding, which behaves as it does today at every background. A gap between
   items is filled with the background, or with a neutral solid when the background is `none`.
   A manual export frame overrides the content box; the crop tool becomes that frame.
   A canvas holding one untouched image exports what the current editor exports.
3. **Three artifacts.** `<id>.png` (flattened, always valid), `.kaipu/<id>.canvas.json` (the
   document, with `schemaVersion`), `.kaipu/<id>.assets/` (each image as added).
4. **The flattened PNG is the fallback.** If the document or an asset cannot be read, the
   editor opens `<id>.png` as a single image item.
5. **Redaction is destructive at save.** The redacted pixels are replaced in the stored
   asset. The redaction stays in the document as a locked item. The styles are a strong blur (the
   region is reduced to coarse blocks, then smoothed) and `solid`. Only `solid` hides content
   for certain: block averages of short, predictable text can be matched against rendered
   candidates, so the strong blur has a minimum block size and the tool states the difference; the light gaussian that `annotations/tools.ts` documents as
   reversible is retired, so it is never the thing baked into an asset.

## Implementation status

M3 ([NIW2-700](https://linear.app/niway/issue/NIW2-700)) builds points 3–5 behind the
`image-canvas` flag. M6 ([NIW2-703](https://linear.app/niway/issue/NIW2-703)) adds more images
and moves the document to world units (see "Several images" below).

- **Files.** `<id>.png`, `.kaipu/<id>.canvas.json` and `.kaipu/<id>.assets/base.png`. The
  document and the assets are vault companions: rename, move and delete carry them.
- **Write order.** The PNG first, then the assets, then the document (atomic) last, so a crash
  leaves a valid PNG. A crash between the assets and the document can leave the previous
  document over the new `base.png` (the older annotations on pixels that may carry newer
  redactions); per-save asset ids would remove that window and are a follow-up. If the canvas part fails, the document is
  removed and the save still succeeds. A save without a document (flag off) deletes both.
- **Coordinates.** Annotations stay normalized to the base image, as in M2, and may fall outside
  0–1. Item 0 is the base image at 0,0 with its pixel size. World units arrive with the second
  image (M6); the document's `schemaVersion` is what lets that migration happen.
- **Strong blur.** Block size `max(24, ceil(min(w, h) / 4))` pixels of the region: block
  averages, then bilinear smoothing, so the output depends only on the averages. `solid` fills
  with RGB(26, 26, 26). The light gaussian is no longer offered in canvas mode; with the flag
  off it is unchanged.
- **Locked items.** During a session a redaction stays editable, because the editor keeps the
  unredacted pixels in memory. The saved document marks it `locked`; after reopening it is part
  of the asset and draws nothing of its own.
- **Several images (M6).** Add image (a new capture or a Library item) and paste put an image
  item on the canvas; the select tool moves and deletes it. Each one is its own asset,
  `.kaipu/<id>.assets/img-<random>.png`. The base image stays the anchor (item 0, not
  selectable or movable): whether it should become an ordinary item is an open question for the
  owner on NIW2-703. Radius and shadow apply to every image item. A capture taken for the canvas
  goes back to the editor only: main skips the capture policy, so it is never saved or copied
  on its own.
- **World units on disk (schema version 2).** Every saved geometry is in world units, one unit
  per source pixel of the base image, which sits at 0,0 with its pixel size. Inside the editor
  the geometry stays normalized to the base, the M2 model, because the base is the anchor: the
  two differ only by the base's pixel size, so the conversion is one multiply at save and one
  divide at open, in `canvas-doc.ts`. Strokes, font sizes and seeds are not geometry and are
  stored as before. A version 1 document opens unchanged (it holds one image, so it needs no
  conversion); every save writes version 2. An older build reads a version 2 document as
  unsupported and opens the flattened PNG, the fallback of point 4.
  - _Why world units now, not at the first movable base._ The disk format is the part that
    must be readable forever. Base-normalized coordinates on disk would need a second breaking
    version the day the base moves or stops being item 0, and this ADR reopens on a second
    breaking change. World units make the document independent of which image is the anchor.
  - _Rejected: world units inside the editor too._ Every geometry helper (`handles.ts`,
    `crop.ts`, `compositor.ts`, the annotation layer) would change with no visible result
    while the base is the anchor. That rewrite belongs to the milestone that makes the base
    movable, if the owner chooses it.
- **Redaction over several images.** A redaction is baked into every image it overlaps, the
  base and each added image, whatever their order. The pixels under an image on top are not
  visible, but they are still on disk. On screen and in the export, a redaction draws at its
  z-position the redacted base and the redacted images below it, so it covers the
  annotations under it and never paints over an image above it.
- **Not built.** "Reset edits" and keeping an unredacted original (from the re-editable
  screenshots analysis) contradict a destructive redaction and are left out.

## Alternatives rejected

- **Keep one image per editor and add a separate "board" feature.** Two editors with two
  scene models, and the annotation tools built twice.
- **Flatten only, as today.** Text outside the image and a second image can be flattened, but
  nothing can be moved after saving, which the owner asked for.
- **Save redacted screenshots flattened only** (the recommendation in the earlier analysis).
  It was the cheap answer when re-editing was optional; with a canvas of several images,
  dropping the document because one of them has a redaction loses the whole layout.
- **Adopt a canvas library (Konva, Fabric, tldraw).** The SVG layer and Canvas 2D compositor
  already select, draw and export every annotation kind; a library replaces working code and
  adds a dependency for pan and zoom, which are a transform.

## Consequences

- Annotation coordinates migrate from normalized-to-shot to world units; every geometry
  helper (`handles.ts`, `crop.ts`, `compositor.ts`) changes.
- The document format must be readable forever: `schemaVersion` and a migration per bump.
- Storage per item roughly doubles (asset plus flattened).
- A redaction cannot be undone after saving.
- Cloud sync keeps carrying only `<id>.png`; an item downloaded on another machine is flat.

## Non-goals

Cloud sync of the document, layout helpers, layers UI, multi-page documents, collaboration.

## What would reopen this

- One-image parity cannot be kept without special cases in the compositor.
- The document needs a second breaking schema change within its first three versions.
- Cloud sync of editable items is scheduled: the asset and document transport needs its own decision.
